# Контекст проекта для AI-агентов

## Кратко о продукте

**Название:** «Бестиарий растений».

**Цель:** сделать понятный образовательный веб-справочник, в котором посетитель может найти растение и получить краткую информацию по поисковому запросу.

**Текущее состояние по имеющейся информации:** HTML-страница и макет Figma уже подготовлены. Необходимо проверить их реальные пути и URL Figma. Фактический стек проекта, состояние backend, BM25, LLM и API следует определить по содержимому репозитория, а не предполагать.

**Целевая идея:** пользователь вводит название растения или вопрос → система ищет подходящие сведения в документном корпусе при помощи BM25 → при наличии контекста LLM составляет grounded-ответ → интерфейс показывает результат и источники. Этот поток является целевым, а не утверждением о текущем состоянии реализации.

## Пользователи и задача

Основной предполагаемый пользователь — учащийся, студент или любознательный человек, которому нужно быстро узнать особенности растения и понять, откуда получена информация.

Главная потребность: получить структурированный ответ, который можно проверить по источникам, а не просто неподтверждённый текст.

## Границы продукта

В базовую концепцию входят:

- поиск по названию/вопросу;
- представление найденной информации в понятном интерфейсе;
- отображение происхождения информации/источников в целевой RAG-версии;
- корректное состояние при пустом запросе, отсутствии результатов и ошибке;
- дальнейшая оценка качества поиска на фиксированном наборе benchmark-запросов.

Не следует считать частью MVP без отдельного решения:

- распознавание вида по фотографии;
- пользовательские аккаунты, избранное и социальные функции;
- медицинские рекомендации или диагнозы;
- автоматическое определение съедобности;
- гарантированно исчерпывающий каталог всех видов;
- обещание, что LLM всегда отвечает без ошибок.

## Важное допущение — подтвердить с владельцем проекта

В предыдущем варианте документации рабочим допущением были **реальные растения**. Название «Бестиарий» может означать и вымышленные виды. Перед созданием корпуса, prompt-ов и примеров интерфейса AI должен проверить спецификацию или спросить владельца, если от этого зависит задача. Не изменять концепцию молча.

## Источники истины в репозитории

Перед задачей найди актуальные документы. По планируемой структуре:

- `README.md` — текущее описание, структура и запуск;
- `docs/SDD.md` — индекс спецификации;
- `docs/product/` — цель продукта, требования, пользовательские истории;
- `docs/interface/` — HTML/Figma и поведение интерфейса;
- `docs/architecture/` — компоненты и интеграционные контракты;
- `docs/retrieval/` — корпус, BM25, benchmark;
- `docs/team/` — владельцы областей и процесс работы;
- `docs/decisions/` — принятые архитектурные решения;
- `docs/testing/` — тестовые сценарии.

Если часть этих путей отсутствует, не создавай автоматически дублирующую альтернативную документацию: определи существующую организацию проекта и согласуй/адаптируй ссылки.

## Как судить о текущем статусе

Различай три статуса:

- **Реализовано и проверено** — код существует и проверка запускалась.
- **Реализовано частично / mock** — есть заглушка, демо-данные или частично работающая функция.
- **Запланировано** — описано в спецификации, но кода ещё нет.

Не превращай статус «запланировано» в «готово» только потому, что он описан в документации.

# Спецификация корпуса документов

**Назначение:** согласовать состав данных, происхождение, поля записей и подготовку индекса для поиска по растениям.

## 1. Принципы корпуса

- У каждой записи есть стабильный `document_id`.
- Источник происхождения фиксируется; нельзя копировать текст без отслеживания его источника и условий использования.
- Имена растений нормализуются, но исходные формулировки сохраняются там, где они важны для поиска.
- Факты о токсичности, лечебных свойствах и употреблении не добавляются без проверяемого авторитетного источника.
- Дубли и почти идентичные страницы выявляются до построения индекса.
- Если данных недостаточно, запись не дополняется догадками.

## 2. Состав одной записи

Рекомендуемая структура JSONL: одна JSON-запись на строку. Минимальный обязательный набор — ID, название/текст и источник; остальные поля заполняются по наличию данных.

```json
{
  "document_id": "plant-0001",
  "plant_name": "Венерина мухоловка",
  "scientific_name": "Dionaea muscipula",
  "aliases": ["венерина мухоловка"],
  "category": ["хищное растение"],
  "content": "Проверенное описание растения...",
  "source_title": "Название публикации или справочника",
  "source_url": "https://example.org/source",
  "publisher": "Издатель или организация",
  "published_at": null,
  "accessed_at": "YYYY-MM-DD",
  "language": "ru",
  "license_or_usage_note": "Проверить условия использования до включения в корпус"
}
```

Это иллюстративный шаблон. URL, дата и содержание должны быть заменены реальными значениями перед использованием.

## 3. Пояснение полей

| Поле | Тип | Обязательность | Назначение |
|---|---|---|---|
| `document_id` | string | Обязательно | Стабильный уникальный ключ |
| `plant_name` | string | Желательно | Распространённое русское название |
| `scientific_name` | string/null | По наличию | Научное название, если подтверждено источником |
| `aliases` | string[] | По наличию | Синонимы и варианты запроса |
| `category` | string[] | По наличию | Например, хищное растение; назначать только обоснованные категории |
| `content` | string | Обязательно | Очищенный текст документа или фрагмента |
| `source_title` | string | Обязательно, если известен | Название источника |
| `source_url` | string/null | По наличию | URL первоисточника |
| `publisher` | string/null | Желательно | Автор/организация/издатель |
| `published_at` | date/null | По наличию | Дата публикации источника |
| `accessed_at` | date | При сборе | Дата доступа к веб-источнику |
| `language` | string | Желательно | Язык текста, например `ru` или `en` |
| `license_or_usage_note` | string | Желательно | Лицензия, разрешение или заметка по правам |

## 4. Правила подготовки

1. Определить и согласовать список источников.
2. Сохранять библиографические сведения вместе с текстом.
3. Удалять навигацию, рекламу и нерелевантные элементы, не искажая смысл.
4. Делить слишком большие тексты на фрагменты; каждому фрагменту назначать ID, связанный с исходным документом.
5. Применять одинаковую нормализацию текста для запроса и корпуса (регистр, пробелы, пунктуация; стемминг/лемматизация — только если команда решила использовать это для BM25 и проверит влияние на качество).
6. Проверять дубликаты и пустые записи.
7. Версионировать подготовленные данные и фиксировать число документов и способ обработки.
8. До включения в репозиторий проверить лицензии и требования к распространению; большие исходные тексты могут храниться вне Git, а в репозитории — схема, небольшие разрешённые примеры и инструкция загрузки.

## 5. Политика содержания

- Не включать неподтверждённые медицинские советы.
- Не утверждать, что растение съедобно или безопасно, если это не подтверждено надёжным источником.
- Не смешивать вымышленные и реальные виды без маркировки. Для текущей спецификации рабочее допущение — реальные растения.
- Если у двух источников конфликтующие сведения, сохранять оба источника и отметить конфликт для проверки, а не скрывать его молча.

## 6. Минимальная проверка качества корпуса

- уникальность `document_id`;
- непустые поля `content`;
- источник у каждой публикации, используемой для ответа;
- отсутствие лишних дублей;
- корректная кодировка UTF-8;
- проверка случайной выборки записей человеком;
- возможность из результата поиска восстановить ссылку на исходный документ.

## 7. Рекомендуемое размещение

На ранней стадии: `data/examples/` для нескольких разрешённых демонстрационных записей и `data/README.md` для инструкции подготовки корпуса. Полный индекс, временные файлы и локальные наборы не следует бездумно коммитить в Git; правила хранения определить по размеру и лицензии.

# Спецификация интерфейса

**Источник визуального решения:** существующие Figma-макет и HTML-прототип.  
**Назначение:** описать поведение элементов, чтобы продуктовая и техническая части одинаково понимали интерфейс.

## 1. Основные области экрана

Точные расположение, цвет, типографика и декоративные элементы определяются уже существующим макетом Figma. С точки зрения поведения главная страница содержит следующие смысловые области (если они предусмотрены текущим дизайном):

1. **Шапка:** название «Бестиарий растений» и навигация, если она есть.
2. **Ввод запроса:** текстовое поле для названия растения или вопроса и действие отправки.
3. **Основная область результата:** ответ или список найденных растений/документов.
4. **Источники:** список документов, на которых основан ответ, когда backend возвращает такие данные.
5. **Обратная связь:** состояния загрузки, отсутствия результатов и технической ошибки.

## 2. Поведение поля запроса

- Подсказка должна объяснять, что можно ввести название или вопрос.
- Пробелы в начале и конце не должны мешать отправке; запрос, состоящий только из пробелов, считается пустым.
- Во время запроса показывается состояние загрузки.
- Если запрос уже выполняется, повторное нажатие не должно создавать несколько одинаковых запросов, если реализация позволяет это контролировать.
- После получения результата пользователь может изменить запрос и отправить новый.

## 3. Карточка растения / результат поиска

Поля отображаются только при наличии данных:

- распространённое название;
- научное название (если известно и проверено);
- краткое описание;
- категория или примечание, если это предусмотрено корпусом;
- ссылка на источник.

Не следует заполнять отсутствующие значения вымышленными характеристиками. Если источник не содержит сведений о поле, оно не показывается либо отмечается нейтрально как неизвестное.

## 4. Состояния интерфейса

| Состояние | Что видит пользователь | Условие |
|---|---|---|
| Начальное | Поле запроса и краткое объяснение возможностей | Страница открыта, запрос ещё не отправлен |
| Загрузка | Индикатор или текст ожидания | Запрос отправлен, ответ ещё не получен |
| Результат | Ответ и/или карточки найденных материалов | Поиск вернул релевантные данные |
| Пустая выдача | Сообщение, что ничего подходящего не найдено, и совет уточнить запрос | Поиск выполнен, результатов нет |
| Недостаточно данных | Сообщение, что корпус не позволяет уверенно ответить | Результаты не подтверждают ответ на вопрос |
| Ошибка | Нейтральное уведомление и возможность повторить запрос | Сеть, backend, поиск или LLM недоступны |

На первой контрольной точке эти состояния могут быть описаны в документации и Figma, даже если часть из них пока не реализована в HTML.

## 5. Источники и доверие

- Источник должен быть визуально отделён от текста сгенерированного ответа.
- Название и URL берутся из метаданных документа, а не формируются моделью.
- Если список источников пуст, интерфейс не должен показывать фиктивные ссылки.
- Предупреждения о токсичности или рисках отображаются только тогда, когда они подтверждаются источником из корпуса.

## 6. Доступность и адаптивность

- Элементы управления имеют понятные текстовые подписи или доступные названия.
- Контраст текста и фона достаточен для чтения.
- Формы и результаты не должны требовать горизонтальной прокрутки на обычной мобильной ширине.
- Ошибки и статусы не должны обозначаться исключительно цветом.
- Изображения (если есть) снабжаются осмысленным альтернативным текстом.

## 7. Соответствие реализации

Перед сдачей отметить для каждого пункта одно из состояний: **реализовано**, **показано только в Figma**, **запланировано**. Не обещать в README функциональность, которую HTML фактически не выполняет.

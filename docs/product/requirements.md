# Требования к продукту и критерии приёмки

**Документ:** SDD / Product requirements  
**Версия:** 1.0  
**Статус:** спецификация целевого MVP; требования к будущим компонентам не означают, что они уже реализованы.

## 1. Границы продукта

MVP — веб-интерфейс для поиска по коллекции материалов о растениях. Планируемая архитектура включает frontend, backend/API, поисковый модуль BM25, корпус документов и внешний или локальный вызов LLM для подготовки ответа по найденному контексту. Текущий HTML-прототип может работать на демонстрационных данных.

## 2. Функциональные требования

| ID | Требование | Приоритет | Критерий приёмки |
|---|---|---|---|
| FR-01 | Пользователь может ввести текстовый запрос | Must | Поле доступно на главном экране; введённый текст можно отправить кнопкой и, если это предусмотрено текущей реализацией, клавишей Enter |
| FR-02 | Пустой запрос не запускает поиск | Must | При отправке пустого или состоящего из пробелов поля показывается понятная подсказка; запрос не отправляется в backend |
| FR-03 | Поиск должен поддерживать запрос по названию или вопросу | Must for MVP | После подключения backend запрос передаётся в поисковый модуль; на контрольной точке допустима заглушка, явно обозначенная как демо |
| FR-04 | Система должна отображать релевантные результаты | Must | Для каждого результата доступны название и краткое описание; дополнительные поля показываются, только если есть в данных |
| FR-05 | Ответ, построенный LLM, должен опираться на найденный контекст | Must for RAG stage | Интеграционный тест проверяет, что в генерацию переданы найденные фрагменты, а не только исходный вопрос |
| FR-06 | Ответ должен предоставлять источники | Must for RAG stage | Для каждого показанного источника доступны название документа и, если источник находится в сети, URL; интерфейс не создаёт ссылки, которых нет в данных |
| FR-07 | При отсутствии релевантных данных система сообщает об этом | Must | Пользователь видит сообщение об отсутствии результатов или недостатке данных; система не выдаёт неподтверждённый факт как достоверный |
| FR-08 | Интерфейс должен иметь состояние загрузки | Must | При ожидании ответа пользователь видит индикатор или сообщение; повторная отправка не должна случайно дублировать запросы, если запрос уже выполняется |
| FR-09 | Ошибки поиска или генерации отображаются понятно | Must | При технической ошибке показывается нейтральное сообщение и возможность повторить запрос; технический stack trace не показывается пользователю |
| FR-10 | Интерфейс показывает базовую информацию о растении | Should | Карточка при наличии данных показывает обычное и научное название, краткое описание и источник |
| FR-11 | Система не выдаёт медицинские или опасные рекомендации | Must | Запрос об употреблении/лечении/обращении с неизвестным растением не получает опасных инструкций; при необходимости система сообщает о границах проекта |
| FR-12 | Пользователь может выполнить новый запрос | Must | После получения результата пользователь может изменить запрос без перезагрузки страницы, если это поддерживает текущая реализация |

## 3. Нефункциональные требования

| ID | Требование | Критерий приёмки / способ проверки |
|---|---|---|
| NFR-01 | Читаемость | Основные тексты, поле поиска и результаты различимы на desktop и мобильной ширине; нет перекрытия основных элементов |
| NFR-02 | Воспроизводимость запуска | Новый участник может запустить имеющийся HTML по README без неописанных шагов |
| NFR-03 | Трассируемость ответа | В целевом RAG-режиме источники связываются с конкретными найденными документами |
| NFR-04 | Разделение секретов | API-ключи не хранятся в HTML, Git или публичной конфигурации; доступ к LLM выполняется через backend |
| NFR-05 | Обрабатываемость ошибок | Таймаут, пустая выдача и недоступность LLM не приводят к падению пользовательского интерфейса |
| NFR-06 | Поддерживаемость | Контракт API, формат документов и ключевые решения описаны в `docs/` |
| NFR-07 | Согласованность | Имена полей и статусы компонентов не противоречат друг другу в продуктовой, интерфейсной и технической документации |

Количественные показатели времени ответа и качества поиска следует измерить на доступном корпусе и инфраструктуре. До измерения не заявлять SLA или гарантированное качество.

## 4. Вне рамок первой контрольной точки

- работающий BM25 и сохранённый индекс;
- реальный вызов LLM и production RAG pipeline;
- гарантированная полнота корпуса;
- benchmark с измеренными итоговыми метриками, если код поиска ещё не готов.

На первой точке достаточно зафиксировать требования, архитектуру, схему данных и план измерения.

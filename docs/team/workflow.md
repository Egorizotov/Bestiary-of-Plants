# Командный процесс и Git

## 1. Как вести задачи

Для каждой задачи зафиксируйте: название, ответственного, входные зависимости, результат, критерий приёмки и статус (`todo`, `in progress`, `review`, `done`). Подойдёт GitHub Issues, доска проекта или простая таблица — важно одно согласованное место для статусов.

## 2. Рабочий цикл

1. Перед началом задачи владелец убеждается, что требования и формат входных/выходных данных понятны.
2. Для изменения спецификации сначала обновляется соответствующий файл в `docs/`.
3. Изменение реализации делается в отдельной ветке, если команда использует ветвление.
4. Перед слиянием проверяются критерии приёмки и локальный запуск.
5. После слияния владелец обновляет статус задачи и документации.

## 3. Имена коммитов

Используйте короткие сообщения, описывающие изменение:

```text
docs: add product brief
docs: define checkpoint 1 deliverables
feat(ui): show empty search state
feat(retrieval): add BM25 baseline
fix(api): handle empty query
chore: document local run
```

В реальных коммитах уберите лишний начальный пробел перед второй строкой примера. Не коммитьте API-ключи, локальные `.env`, временные индексы или скачанные корпуса с неясными условиями использования.

## 4. Definition of Done

Задача считается выполненной, если:
- результат соответствует критерию приёмки;
- связанные тесты или ручные проверки выполнены;
- документация обновлена, если изменились интерфейс, схема данных, API или запуск;
- изменение закоммичено и доступно остальным;
- владелец может кратко объяснить своё изменение.

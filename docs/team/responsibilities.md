# Зоны ответственности команды

Зоны ответственности постоянные. Каждый участник должен понимать весь пользовательский путь и уметь запустить проект, даже если отвечает только за одну часть реализации.

## 1. Матрица ответственности

| Работа / артефакт | Участник A: продукт и интерфейс | Участник B: корпус и поиск | Участник C: интеграция |
|---|---|---|---|
| Product brief и пользователь | Ответственный | Консультирует | Консультирует |
| Пользовательские истории и требования | Ответственный | Консультирует по ограничениям поиска | Консультирует по ограничениям API |
| Figma и HTML | Ответственный / автор текущего UI | Консультирует по типам данных | Проверяет интеграционные состояния |
| Схема корпуса | Консультирует по нужным полям карточки | Ответственный | Согласует формат данных |
| BM25 и benchmark | Консультирует по реальным запросам | Ответственный | Помогает подключить endpoint |
| Архитектура и API-контракт | Согласует UI-поля | Согласует документ и score | Ответственный |
| Общий запуск | Проверяет запуск UI | Проверяет запуск поиска, когда готов | Ответственный за общую инструкцию |
| README, Git и контрольная точка | Совместно | Совместно | Координирует, если назначен |

## 2. Обязанности по ролям

### Участник Егор И.Ф. — продукт и интерфейс

**Должен сделать:**
- поддерживать согласованное описание пользователя и проблемы;
- описать основной сценарий, альтернативы и критерии приёмки;
- сверить готовые HTML и Figma с `interface-spec.md`;
- перечислить реальные состояния интерфейса: начальное, загрузка, результат, пустая выдача, ошибка;
- согласовать, какие поля результата нужны интерфейсу;
- не обозначать демонстрационные данные как результат реального поиска.


### Участник Каргин В.В. — корпус, BM25 и benchmark

**Должен сделать:**
- согласовать типы источников и правила их использования;
- утвердить схему записи вместе с интеграционной ролью;
- подготовить небольшую проверяемую выборку корпуса для дальнейшей разработки;
- спланировать очистку, нормализацию, разбиение и построение индекса;
- привязать benchmark-запросы к реальным документам после наполнения корпуса;
- определить способ оценки и фиксировать версии данных.


### Участник Диана Ш.В. — интеграция

**Должна сделать:**
- поддерживать архитектурную схему полного пути запроса;
- согласовать с frontend и поиском контракт запросов и ответов;
- определить единый формат ошибок и пустой выдачи;
- описать конфигурацию и безопасное хранение секретов для будущего backend;
- подготовить воспроизводимую инструкцию запуска;
- проверить, что проект можно клонировать и открыть без неописанных ручных шагов.
- запарсить данные

## 3. Общие правила

- У каждого документа и компонента один ответственный за актуальность.
- Изменения общего сценария, схемы данных или API согласуются до реализации.
- Участник, изменивший контракт, обновляет связанную документацию и уведомляет затронутых владельцев.
- Каждый участник должен уметь объяснить: пользователь → frontend → backend → BM25 → найденный контекст → LLM → ответ и источники.
- Отсутствие полной реализации на первой точке не маскируется; будущие компоненты отмечаются как планируемые.

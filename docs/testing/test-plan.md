# План проверок

**Статус:** план проверок; часть пунктов применима после реализации backend/RAG.

## 1. Проверки первой контрольной точки

| ID | Проверка | Шаги | Ожидаемый результат |
|---|---|---|---|
| CP-01 | Открытие HTML | Запустить инструкцию из README | Страница открывается без отсутствующих ресурсов и критичных ошибок |
| CP-02 | Соответствие Figma | Сопоставить заголовок, поле запроса, основной результат | Документация и интерфейс используют одинаковые названия и смысл |
| CP-03 | Ссылка Figma | Открыть URL в приватном окне / учётной записи без доступа к рабочей команде, если возможно | Проверяющий может просмотреть макет |
| CP-04 | Пути документов | Открыть все ссылки внутри README и `docs/` | Относительные ссылки ведут на существующие файлы |
| CP-05 | Воспроизводимый запуск | На чистом клоне выполнить команду запуска | Прототип открывается по инструкции без скрытых зависимостей |
| CP-06 | Честность статуса | Сравнить описания функций с реальным HTML | Планируемые функции не описаны как работающие |
| CP-07 | Git | Посмотреть `git status` и `git log --oneline` | Файлы находятся под контролем версий, коммиты имеют понятные сообщения |

## 2. Ручные проверки интерфейса

- поле запроса видно и понятно;
- пустое значение обрабатывается либо явно помечено как незавершённое;
- длинный запрос не ломает layout;
- результат читается и отделён от навигации;
- на узком экране основные элементы не перекрываются;
- изображения имеют разумные размеры и не ломают карточки;
- ссылки открываются корректно;
- если результат демонстрационный, это не маскируется под настоящую выдачу.

## 3. Проверки после реализации API

- запрос с валидным текстом возвращает структурированный ответ;
- пустой запрос возвращает `400` или `422` согласованного формата;
- `limit` ограничивается допустимым диапазоном;
- пустая выдача корректно отображается;
- временная недоступность поиска/LLM возвращает понятную ошибку;
- backend не раскрывает stack trace и ключи;
- источники в ответе существуют и соответствуют ID использованных документов;
- ответ при недостатке контекста не выдумывает конкретные факты.

## 4. Проверки поиска и RAG после реализации

- запустить тестовый набор из `../retrieval/benchmark.md`;
- сохранить версии корпуса, индекса и настроек;
- рассчитать Recall@5 / Precision@5 на запросах с эталонными документами;
- вручную проверить корректность ответов, источников и отказов от ответа;
- отдельно проверить токсичные/медицинские запросы на отсутствие опасных инструкций;
- документировать известные ограничения.

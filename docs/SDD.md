# SDD — спецификация проекта «Бестиарий растений»

**Версия:** 1.0  
**Статус:** базовая спецификация для первой контрольной точки  
**Область:** продукт, интерфейс, архитектура и данные для будущего поиска/ответов по корпусу.

## 1. Назначение документа

Этот файл является точкой входа в Spec-Driven Development (SDD) проекта. Он связывает продуктовую цель с требованиями, пользовательскими сценариями, интерфейсом, архитектурой, корпусом и проверками. Подробности хранятся в отдельных тематических файлах, чтобы у каждой части был понятный владелец и чтобы изменения можно было проследить.

## 2. Спецификация продукта

**Проблема:** сведения о растениях могут быть разбросаны по разным источникам; пользователю трудно быстро найти и проверить нужный факт.  
**Решение:** веб-справочник, в котором можно искать по названию или задавать вопрос. В целевой реализации запрос сопоставляется с корпусом документов посредством BM25, а LLM формирует краткий ответ на основе найденного контекста и возвращает использованные источники.  
**Основной пользователь:** учащийся/студент или любознательный пользователь, которому нужно быстро разобраться в особенностях растения.  
**Основной сценарий:** ввод запроса → поиск документов → краткий ответ/карточки → переход к источникам.  
**Ограничение области:** проект не определяет растения по изображениям и не предоставляет медицинских советов.

Рабочее допущение версии 1.0 — каталог посвящён реальным растениям. Если исходное задание требует фантазийный бестиарий, это решение необходимо пересмотреть до наполнения корпуса.

## 5. Процесс изменения требований

1. Зафиксировать причину изменения и затронутый пользовательский сценарий.
2. Обновить основной документ — требование, сценарий, контракт или схему корпуса.
3. Проверить ссылки на связанные артефакты в таблице выше.
4. Согласовать изменение со всеми затронутыми владельцами компонентов.
5. Реализовать изменение и выполнить указанные проверки.
6. Коммитить документ и соответствующую реализацию согласованно.

## 6. Что считается готовым для первой точки

- продукт, аудитория и основной сценарий сформулированы;
- требования имеют ID и критерии приёмки;
- интерфейс описан, существующий HTML и Figma указаны точными путями/ссылками;
- архитектура и границы будущего API понятны;
- определены схема корпуса и план benchmark;
- распределение ответственности и инструкция запуска доступны в репозитории;
- команда явно разделяет уже реализованные части и будущие компоненты.

Полноценный RAG не обозначается критерием готовности первой точки, поскольку по переданным команде условиям на этой стадии он не обязателен.

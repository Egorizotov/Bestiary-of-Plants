# ADR-001: Область MVP и границы первой контрольной точки

- **Статус:** принято как рабочее допущение версии 1.0; пересмотреть, если исходное задание явно задаёт иную область
- **Дата:** 2026-10-10
- **Решение принимается:** вся команда

## Контекст

Команда разрабатывает учебный проект «Бестиарий растений» с разделением работ на продукт/интерфейс, корпус и BM25/RAG, интеграцию. На первой контрольной точке нужны описание продукта и пользователя, документация SDD, интерфейсный прототип, структура репозитория, распределение ролей и инструкция запуска. По условиям, переданным командой, работающий RAG в этой точке не обязателен.

## Решение

1. Для рабочей версии «Бестиарий растений» трактуется как справочник реальных растений; название допускает стилизованную подачу.
2. Главный сценарий — найти растение по названию или задать вопрос о его свойствах и получить краткую справочную информацию.
3. Целевая поисковая цепочка: frontend → backend → BM25 → релевантные фрагменты → LLM → ответ с источниками.
4. BM25 выбран в качестве простого базового метода, который можно оценить на фиксированном benchmark перед добавлением более сложных методов.
5. Первый checkpoint сфокусирован на согласованной спецификации, макете, текущем HTML, структуре репозитория и распределении ответственности; работающий RAG не заявляется обязательным.
6. Проект не предоставляет медицинские советы и не гарантирует определение растения по фотографии.

## Последствия

- Продуктовые документы можно использовать как основу следующего этапа.
- Команде нужно проверить, соответствует ли допущение о реальных растениях исходной теме задания. Если проект подразумевает вымышленные виды, скорректировать этот ADR, brief, корпус и benchmark до начала сбора данных.
- API-контракт является проектным и должен быть подтверждён разработчиками перед кодированием.
- Целевые метрики benchmark остаются предложениями до первого реального прогона.

## Альтернативы

- Сразу делать только каталог без генеративных ответов: проще, но не демонстрирует целевую RAG-интеграцию.
- Сразу внедрять гибридный/векторный поиск: потенциально полезно, но усложняет раннюю базовую реализацию и не позволяет сравнить качество с простым BM25.
- Делать определение растений по изображению: вне текущего объёма и требует отдельного набора данных и отдельной проверки качества.

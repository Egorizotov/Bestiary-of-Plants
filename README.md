# Бестиарий растений

**Тип проекта:** веб-справочник с поиском по коллекции документов и ответами на вопросы пользователя.  
**Этап:** контрольная точка 1 — формализация продукта и подготовка к реализации.  
**Версия документации:** 1.0  
**Статус реализации:** интерфейсный HTML-прототип и макет Figma подготовлены; поисковый модуль BM25, корпус, вызов LLM и полноценный RAG являются следующими этапами, если они ещё не реализованы в текущей ветке.

## 1. Что это за продукт

«Бестиарий растений» — интерактивный справочник для изучения необычных, интересных и заметных видов растений. Пользователь может искать растение по названию или задавать вопрос на естественном языке. Планируемая поисковая версия находит подходящие фрагменты в подготовленном корпусе с помощью BM25 и формирует краткий ответ на их основе с указанием источников.

**Рабочее допущение для этой версии:** речь идёт о реальных растениях, включая необычные, хищные и потенциально опасные виды. Проект не является медицинским сервисом и не должен давать инструкции по употреблению, лечению или безопасному обращению с неизвестными растениями. Если согласованная тема предполагает вымышленные растения, допущение нужно изменить в `docs/decisions/ADR-001-scope.md` и связанных требованиях.

## 5. Локальный запуск HTML-прототипа

Если `index.html` находится в `frontend/` и использует только статические HTML/CSS/JS-ресурсы:

```bash
python -m http.server 8000 --directory frontend
```

Откройте в браузере `http://localhost:8000/`.

Если Python не установлен, откройте HTML локально двойным щелчком либо используйте локальный сервер, принятый в команде. Если HTML зависит от путей, модулей или API, запускать его нужно способом, указанным в самом проекте. Команда выше запускает только статический прототип и **не** запускает BM25, backend или LLM.

## 6. Распределение ответственности

| Направление | Владелец по роли | Основной результат |
|---|---|---|
| Продукт и интерфейс | Участник A — указать имя в `docs/team/responsibilities.md` | Продуктовая SDD, сценарии, UI-спецификация и согласованный HTML/Figma |
| Корпус, BM25 и benchmark | Участник B — указать имя | Формат записей, правила подготовки корпуса, план оценки поиска |
| Интеграция | Участник C — указать имя | Архитектура, API-контракт, общий путь запроса и инструкция запуска |
| Координация и Git | Все; координатор назначается командой | Репозиторий, согласование документации, история изменений и демонстрация |

В команде из двух человек объедините роли B и C либо A и C — главное, чтобы у каждого артефакта был один ответственный, а решения согласовывались с остальными.

## 7. Рабочий процесс разработки

1. Изменение требований начинается с правки соответствующего файла в `docs/`.
2. Команда согласует изменения, которые затрагивают сценарий, формат данных или контракт API.
3. Реализация делается небольшими коммитами с понятными сообщениями.
4. Перед слиянием проверяются затронутые требования и инструкция запуска.
5. В документации отмечаются только фактически реализованные возможности; запланированные пункты помечаются как «планируется».

Примеры сообщений коммитов:

```text
docs: add product brief and acceptance criteria
docs: describe UI states and existing prototype
docs: define retrieval corpus and benchmark
chore: add checkpoint 1 repository documentation
```

## 8. Критерий готовности первой точки

Контрольная точка готова, когда по репозиторию понятно, **что строит команда, для кого, как выглядит основной сценарий, какие компоненты планируются, кто за что отвечает и как открыть текущий прототип**. Полноценный RAG на этом этапе не обязателен согласно условиям контрольной точки, приведённым в исходном задании команды.
